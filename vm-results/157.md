## Blocker

B1. Editing the Combat rules text on Settings -> RPG uses up the chat's retained-pin budget, and after about 8 to 13 distinct edits
every new text is refused with "Combat rules: Retained pin budget exhausted; nothing applied."
The same budget is shared by every block action (define, redefine, pin), so the chat can also no longer make a new character
(the wizard's `dm.define`) or edit any other chat block.

- Path: the page's `save()` calls `dm.redefine` (src/v2/lean-rpg/view/settings.js:~176, `withPrompt` in
  src/v2/lean-rpg/view/settings-data.js:~33). `changeBlock` (src/v2/data-modules/part.js:413) writes
  `draft.pins[hash] = pin` for every new definition hash and never drops the pin of the definition it replaces.
  `finish` (part.js:326) refuses once `Object.keys(draft.pins).length > L.pins` (16, schema.js:15) or the pins exceed
  `pinsBytes`. Every distinct prompt text is a new hash, so every edit keeps one more pin.
- Repro (throwaway, kept at /tmp/claude-0/-home-user-inventory-block/3572f065-fdf3-5cf4-88eb-a15358a57ebe/scratchpad/rv-157/repro-pins.test.js;
  run it from the clone as tests/v2/lean-rpg/view/zz-repro-pins.test.js): real testkit host, Wessel's Character and Skills blocks plus
  the Combat rules template (3 active pins), then `dm.redefine` of the Combat block with "Text 1", "Text 2", ... (a new reply every
  second edit). Result: edits 1 to 13 succeed (pins 4 to 16), edit 14 fails with the message above. With the 8-block party the
  template allows, only 8 distinct edits fit.
  - Resetting to the default text still works (its hash is already pinned), but any other new text fails.
  - Deleting the latest reply does not free it (still 16 pins, edit refused).
  - Nothing tells the reader what to do: the status line shows the engine's wording.
- Why it is not "pre-existing": `dm.redefine` and the pin cap are old, but hand-authored role blocks were read-only in the block editor, so
  nothing let a reader redefine a Combat block over and over. R3 adds that path and makes it cheap (one blur per edit), and the brief
  said to check the redefine/pin rules. The lead can downgrade it if the pin cap is accepted as a known limit, but then the page should say so.
- Suggested fixes (lead's choice): (a) in `changeBlock` redefine, delete the replaced hash from `draft.pins` when no other active entry
  uses it (a reply's guard already carries its own `recorded.pin`, so earlier replies replay from their own state); or (b) at least
  turn the refusal into a plain sentence on the page ("This chat has kept as many block versions as it can. Reset to the default,
  or delete some recent replies.") and test it.
