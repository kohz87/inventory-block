## Blockers

### B1. A delay after an "Any time" or place-only parent never comes due when the clock is not yet set at the parent's first firing
Path a writer and a reader hit with a pack made only in Studio's UI. A new event starts as "Any time" (`when: 'true'`, `src/screens/timeline.js:17`). The writer ticks Lasting change on it and adds a second event "After another event, 2 days". The exported pack (repro `ui-made.test.mjs`, output `ui-made.pack.json`) is:
- `the-seal-cracks`: `when: "true"`, `then: [chronicle.lasting { name: 'Seal cracking', state: 'ongoing' }]`
- `the-seal-fails`: `after: the-seal-cracks`, `when: "query('chronicle.passed', { name: 'Seal cracking', minutes: 2880 })"`

Repro (`ui-run.mjs`, SD vendored host, SB 2.7.0): install the pack, reply 1 `~ time June 3, 1200, 08:00 am`, then `! time +3d`, `! time +30d`. `the-seal-cracks` fires before reply 1 (clock still null), so the entry is stored with `since: null` (`chronicle.events` shows `["Seal cracking", null]`). `chronicle.passed` is false for a null `since` forever (`src/v2/chronicle/queries.js:278`), so `the-seal-fails` never fires, 33 story days later it still has not. Nothing says why: the Timeline, Problems and the child's form show no warning.
Same with a pack that has a calendar start (Ersveil-like: the clock is seeded by `director.seed` in the same beforeGenerate, after the event hook already ran): `any-parent` fired on reply 1, entry `Dark omen@null`, child `any-child` never fired (`e2e.mjs`). A place-only parent that matches the start place does the same.
Cause: `since: now` takes the clock as it is at firing (`src/v2/chronicle/capture.js:298,309`, null is deliberate per SPEC), and Studio's `writeCondition` puts no `time() != null` guard on a parent that has a Lasting change (dated parents get it for free, `src/timeline/condition.js:36`). Smallest fixes, either side: Studio adds `time() != null &&` to the `when` of an event with a Lasting change (or refuses "After" under a parent without a guard); or SD `chronicle.lasting` fails (not creates) while the clock is null, so the event waits and retries until the clock exists.
Not pre-existing: `chronicle.passed` and the delay UI are new in this build.

### B2. Without Story Director (or with SD that lacks `chronicle.lasting`) an event with a Lasting change never happens, and Studio says the opposite
Studio tells the writer "Without Story Director the news is still told once" (`src/screens/timeline-form.js:429`, repeated in `docs/STUDIO.md:67`). It is false. Repro (`nosd.mjs`, host with no SD module; same for SD 2.2.0, which has no such command): pack with `plain` (`when: 'true'`, no then) and `omen` (`when: 'true'`, `then: chronicle.lasting`). `plain` fires on reply 1 and its cue is told; `omen` is "due" every reply and fails every reply with `UNKNOWN_COMMAND "chronicle.lasting"` (`events.status.lastRun.failed`), is never claimed, its cue is never told in any prompt, and every event `after` it stays stuck. SB's `createFireEvent` runs the steps before the cue (`vendor events/engine.js:216`) and does not catch UNKNOWN_COMMAND, so SB behaviour is by design; the defect is the promise (a reader with SB + a Studio pack but older or no SD loses the news silently, and that mix is certain during rollout). Fix: Studio's text and doc must say the event does not happen at all without SD (and ideally Problems/export warns when any event has a lasting change), or the news goes in a separate no-then event.

## Follow-ups (not blockers)

1. Journal path: `lastingByRev` keys a fire receipt to the entry's *current* `rev` (`queries.js` lastingByRev). If the entry changes after the fire (a `world` line in the same reply, a later event, a reader edit) the fire's Journal world line comes from the later capture.world receipt or is dropped. Checked: the day line text is stable (saved when the day closes, reader edit afterwards did not change it); only the exact-fire attribution is fragile.
2. Studio's caps check is looser than SD in two hand-edit cases (Advanced `then`): a blank faction (`""`) and unknown payload keys (`aka`, a `Keep` typo) pass `checkLasting` but SD refuses INVALID ("a faction needs a name", "has no X"), so the event fails every reply. The form cannot produce them. It is stricter in one: a name or summary with padding spaces beyond the limit is flagged, SD trims first (harmless). Everything else matches SPEC section 1 (name 80, summary 240, place 80, 4 factions of 80, keep boolean, state words; code points).
3. Removing a Lasting change from the parent, or hand-editing `then`, leaves children's `chronicle.passed` pointing at a name nothing writes: they never fire. Only the child's own form warns; Problems and the list do not. Likewise a lasting rename rewrites only Studio-shaped dependants whose `after` is the renamed event; a hand-written dependant (`... || false`, repro `rename.test.mjs`) keeps the old name silently.
4. The "(so from <parent date> + N days)" preview line counts from the parent's own date; the real count is from the moment the parent fires (the first reply at or after it, in its place), so it can be much later for place-bound parents.
5. Region conditions use `scene.place.region`, which is the story's own region word (carried from `~ place X | region: Y`, empty for a bare `~ place Auvoth`), not the pack place's `region`. The place picker offers the pack's regions, so a region chosen from it may never match. The same is true of the Ersveil events on main (pre-existing); worth one line of help text.
6. Renaming an event (name field = ID) in a pack already played changes the claim key, so the event and its Lasting change fire again in saved chats. Authoring-time only; `Saved as <id>` is shown.
7. Extreme names: a place name containing a raw CR, or over 100 astral characters (emoji), passes Studio's 200 code point check but SB's tokenizer refuses the quoted word (CR unterminated, 200 UTF-16 units). Fuzz of 4000 specs with quotes, backslashes, newlines, tabs, unicode, 190 character names: 0 failures once those two are excluded.
8. `keptEvents` caps the held seats at 2 (verified with 3 kept: held = the 2 most recent), but the third seat is an ordinary pick, so a third `keep: true` entry can appear there by score (never more than 3 in all). Matches the spec wording; stated so nobody expects exactly two.
9. SD: the fuzz-delete generators (`tests/v2/break/fuzz-delete*.test.js`, CLAUDE.md non-negotiable 3) were not extended with `chronicle.lasting`; `lasting-host.test.js` covers swipe, delete, rebuild and reload for the happy path instead.
