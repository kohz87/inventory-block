## Focus findings

**1. `after` ordering (turn.js `linesInOrder`, registry.js).**
- A kind without `after`: `linesInOrder` returns the same array when no line's kind has `after`, so the run is the same as before. Only `~ trip` declares it today. Lines of other kinds keep their order; a moved line goes behind the last line of a named kind written after it and the moved lines keep their order (total order, no tie).
- Receipts, revs and stored ops are written in run order, as before; the reordering happens before the run, so rev numbers rise in the order the lines ran. Problems carry the message index and the line text, not a position in the reply, so nothing there depends on order. Delete and swipe take the whole reply's ops, so they are not affected. Seeds, occurrence plans (`occurrenceFor`) and `opsBefore` are all per kind or per run, and the moved lines of one kind keep their relative order.
- Old chats: stored ops are replayed as stored (nothing re-runs), so an old chat replays exactly. A Re-read of an old reply that wrote `~ trip` before `~ place` runs trip last now: I built that chat with the trip kind's `after` removed, then re-read it with it on: the trip is planned from the new place and mount pace (Hollin's Reach, 35 -> Bluewatch Village, 25 with Burr), the later delay record still attaches, no Problem, a second Re-read changes nothing. The trip record key moves (9.0 -> 11.0, keys are revs). That is the intended fix.
- Only the moved line's seed is lost in that old-order Re-read (`storySeeds` walks the stored receipts with one forward pointer, so a line that now runs after a line that used to follow it gets a fresh seed). Trip records are keyed by rev and use no seed, so it changes nothing today.
- Older host: `after` is an extra key on the kind spec; the old registry validation does not reject unknown keys, so an older host reads the lines as written (the docs say so and a Story Director test pins the new-host part).
- Cycles / unknown words / odd values (a module that declares them; none of ours does): no hang, no throw, one sort. Unknown words, non-array `after` and non-string entries are dropped. A cycle (`aa` after `bb`, `bb` after `aa`) runs `bb` lines then `aa` lines. Not resolved (follow-up 3): a chain (`aa` after `bb`, `bb` after `cc`) runs `aa, cc, bb`, and a kind that names itself reverses its own lines.

**2. Rule (e) (ops.js `heldAlready`, commands.js `ctx.unique`, scene.js).**
- Old ops (no `unique`) replay exactly as before (`op.unique !== true` returns false first). Live commands never use it (`replayed` only). The flag is on the op only, not in state, so heads are identical (checked).
- Lists in a diff are either appended at the end (`add .../-`) or replaced whole, so a removal is always a whole-list `replace`, which the "earlier op wrote the list" test sees. An append is never tested against an item the same block put there (`writtenAbove` ignores `/-` paths on purpose; two appends in one block compare against the state before the block, which is right because two equal names in one command are de-duplicated in `changePresent`).
- Scenarios, each with middle delete, checked against main and against the oracle (`checkInvariants`): `+ present` re-add after a `- present` reply deleted (fixed: Fenna once, the reply's item and coin kept); case variants (`fenna` / `FENNA`: kept once, spelling of the first stays); `+ present Bob, Fenna` / `+ present Fenna, Zed` (Zed still added); delete of the adder or of the re-adder (right result, no skip); reader pencil `scene.present` add (fixed); pencil remove; `+ present` after a `~ place` that cleared the scene. A removed-and-re-added person in an earlier block does not wrongly skip a later add, because replay is in order against the running state.
- A unique append never skipped when it should apply: the only skip condition is that the list already holds the same text (case-insensitive, same as the scene validator), which is exactly the state the validator would otherwise refuse as "listed as present twice".
- Not covered by rule (e) (pre-existing, same on main): see Follow-up 1.

**3. `~ you` (scene.js).** No pack rank: `~ you rank: F-rank | wearing: a grey coat | condition: tired` keeps wearing and condition and gives one Problem; the rank alone is refused whole; `rank:` empty plus another part keeps the other part; the `scene.you` command still refuses a rank; deleting an earlier reply replays clean. Story Director.** Overlapping holds: I ran the 175 repro (foot, Bluewatch to Wolfmere, set out Goldwane 12 8:00, +2 days, delay, +12 h with a second delay, +12 h steps): km along 40, 40, 40, 40, 40, 40, 50, 70, 90, then the leg's end; arrival Goldwane 20 -> 21 -> 22, no drop. ## Follow-ups (none blocks)

1. **`~ place X | with: Name` and the pencil's `set` still skip a whole block after a middle delete.** Same "listed as present twice" fault as the fix, in the two writers that do not call `ctx.unique`. Repro (Story Block, no module): reply a `~ place Inn | kind: settlement` + `+ present Fenna`; reply b `- present Fenna`; reply c `~ place Road | with: Fenna` + `+ item Torch | qty: 2`; delete b. Result: c's place line is skipped (the scene stays at Inn, with a Problem), the torch is kept. Second: reader sets Fenna and Bob in the pencil (`scene.present` with `set`) after b, delete b: the pencil block is skipped and Bob is lost. Identical on main, so not a regression and not what 2.11.1 claims, but a reader can hit it the same way. The remaining failures in my fuzz are all of this form (9 of 9 in the `with:` run with items off; 0 when `with:` is left out). Likely fix: `setPlace` and `setPresent` mark the appends too, or set the list whole.
2. A case variant keeps the first spelling (`fenna` stays when a later `FENNA` is skipped). Cosmetic.
3. `after` is not resolved for chains and a self-naming kind reverses its own lines (see Focus 1). Not reachable today (only `~ trip`, naming kinds that have no `after`). Say so in MODULES, or sort topologically.
4. An old-order Re-read gives the moved line a fresh seed (see Focus 1). Harmless for the trip; a future module that makes seeded records with `after` would see ids change on the first Re-read of an old reply.
5. The `delete-fuzz` file only runs five fixed seeds; seeds 6, 9, 22, 27 fail on a torch-count assertion on main and here. Looks like a fuzz-model limit, not the replay, but worth a look.
6. Fuzz note: `+ item Torch` lines in my own fuzz (an item defined by a reply that is later deleted) give "Item stack ... filed under the wrong ID" Problems on main and here alike; the harness's own "clean input" rule excludes them. Unrelated.
