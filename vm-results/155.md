## Blockers

1. **A valid role block can crash the Party view or allocate an unbounded number of options.** `src/v2/data-modules/check.js:92` accepts any safe integer bounds for a role block; `src/v2/lean-rpg/view/party-data.js:40` uses the field's maximum as the stage count; `src/v2/lean-rpg/view/bars.js:35` builds an array of that size without a bound. Repro: define a chat block with `role: 'character'`, a normal `who` text field, and `health: { type: 'int', min: 0, max: 4294967295, default: 1 }`. Validation and `dm.define` succeed. With RPG on, opening Party calls `drawStageBars` and throws `RangeError: Invalid array length`; smaller still-large maxima can allocate millions of options. A pack or chat block can hit this without bypassing validation.

2. **`prompt: false` fields leak into the role tail.** `src/v2/data-modules/part.js:228` supplies the hidden-field predicate, but `src/v2/lean-rpg/tail.js:35` and `:47` ignore it for skills and foes; `:68` also reads `who` unconditionally. Repro: a validated chat block with `role: 'skills'`, `who` = `Wessel`, `skill1` = `Magic`, and `about1` = `hidden clue: the king is a traitor` with `prompt: false`, and no kinds writing it, is accepted. `summaryOf` returns `Wessel skills:\n- Magic (1): hidden clue: the king is a traitor`. Thus a pack's expressly hidden data is sent to the narrator. This also happens with the RPG feature off because role summaries are unconditional.

3. **The automatic planner is cut off after 2.5 seconds, without its required failure cue.** `src/v2/turn.js:56` and `:394` apply the generic 2.5-second hook timeout to the RPG's 20-second model call in `src/v2/lean-rpg/precall.js:85`; the wrapper times out before the RPG's `skip` path at `:79` can run. Repro: on the real test host with a character and filled foe, make the model answer a valid attack after 3 seconds. Generation proceeds after about 2.5 seconds with zero `rpg.resolve` receipts, no `[Rolls]`, no `No rolls this reply...` cue, and a generic TIMEOUT instead of quiet `ROLLS_SKIPPED`. A normally slow connection therefore narrates an unrolled fight without the specified stop instruction. The merged hook can also lose the other pre-generation outputs collected before the awaited planner returns.

4. **Recorded rolls can be omitted entirely from the narrator's prompt, and the 600-token cue cap is not enforced.** `src/v2/lean-rpg/cue.js:43` refuses to reduce below one round, and checks/refusals are never reduced; `src/v2/prompt.js:193` treats the whole multi-line rolls cue as one removable tail entry. Repro: set Notes per reply to the supported 100-token setting, create three characters with 40-character names and two 40-character foes, and return one act for each character plus two foe attacks. On the real host, a five-line `rpg.resolve` receipt is saved and marked narrated, but `[Rolls]` and its numbers are absent from the request: its 991-character cue was dropped. The battle log then shows rolls the narrator never received. Separately, a valid max-size plan with six acts, four foe attacks and four checks using an Empty skill produced an 815-token cue despite the 600-token limit.

5. **The planner drops unknown and old-style skills instead of rolling them.** The fixed planner format tells the model to omit the stat for any skill (`src/v2/lean-rpg/precall.js:27`, `:37`), while `src/v2/lean-rpg/plan.js:134` and `:172` require either the skill's stored stat or a stat in the answer. Repro: with Wessel and a Rat, `act Wessel | skill: Sword | target: Rat` where Sword is absent returns `{ none: true, dropped: 1 }`, with no untrained roll or refusal note; a pre-G Skills block containing Iron Breath and rank but no `stat1` fails identically for `act Wessel | skill: Iron Breath | target: Rat`. This conflicts with the lead's untrained fallback and the recorded decision that old Skills blocks still work. A fully dropped answer is treated as intentional `none`, so no failure cue is sent either (`precall.js:94`).

6. **The stock Character template lets a narrator kill a healthy character immediately.** `src/v2/lean-rpg/templates.js:54` exposes unconditional `set-alive` as a story kind, bypassing the reply-end latch at `:61`. Repro: create the stock Character with Wessel at Health 5, then capture `~ dm character — fell | kind: set-alive | to: false`. It is accepted without a problem and leaves health 5, down false, alive false, displaying the death card. The same path permits death in the reply that first makes the character Down, contrary to the required prior-reply latch.

7. **Re-reading an earlier reply cannot create a later settlement that was originally unnecessary.** `src/v2/data-modules/part.js:594` and `:621` only record a `dm.settle` when it would change the current state; a later prefix change has no settlement block to replan. Repro: create Character, send reply A with `set-health: Hurt`, then reply B with an accepted `~ place Dungeon | kind: ruin` line. B has no settlement. Edit A to `set-health: Down` and Re-read A. The final state after B is health 0, down true, alive true, including after a cold rebuild. Playing the same final A and B forward makes alive false at B. B has an accepted change, so this is distinct from the lead's known no-accepted-lines follow-up.

8. **The 32-action cap can consume the slot required for `dm.settle`.** Both story actions and the new reply-end action pass through `finish`'s cap at `src/v2/data-modules/part.js:316` and `:591`; no room is reserved for settlement. Repro: add a valid block with one `tick` kind, an enum label with 31 distinct values and `oncePerReply: ['tag']`; in one reply capture those 31 distinct tick lines followed by the stock Character's `set-health: Down`. All 32 story actions are accepted, then `dm.settle` fails `DM_BUDGET`, leaving health 0, down false, alive true. A subsequent reply with an accepted unrelated change only sets down true and leaves the character alive, delaying death by a reply. This is not the already-recorded no-lines case.

9. **The wizard can leave a half-created character at the action cap.** `src/v2/lean-rpg/view/wizard.js:343` issues two independent defines and tries a third budgeted `dm.remove` on failure; `src/v2/lean-rpg/view/wizard-data.js:128` checks pin room but not the reply's remaining actions. Repro: on a reply with 31 data-module actions already used, press Create. The Character define uses action 32; the Skills define fails `DM_BUDGET`; the rollback remove also fails `DM_BUDGET`. The Character remains active without its Skills block, and the reader cannot remove it until a new reply. The existing mock rollback test does not exercise this real failure boundary.

10. **Feature off still imports the RPG core.** `src/v2/domains/index.js:30` statically imports its index and `:304` constructs the part unconditionally; `src/v2/data-modules/check.js:3` imports the same index and `src/v2/data-modules/part.js:14` imports the role tail. Repro on Node 24: register an ESM `load` hook and import `src/v2/domains/index.js` without enabling the feature. It loads `cue.js`, `index.js`, `names.js`, `plan.js`, `precall.js`, `read.js`, `resolve.js`, and `tail.js`. The feature-off fixture tests prompts/draw counts/receipts, not this explicit nothing-imported requirement.

11. **A used planner hold can remain in saved chat metadata.** `src/v2/domains/index.js:243` stops at the first non-null `afterCapture` result; the data-module hook precedes the RPG hook at `:305`. Repro: enable RPG, have the planner return an attack, and have the reply's accepted health line make a Character Down. The reply records `rpg.resolve`, `capture.dm`, and `dm.settle`, but `ctx.chatMetadata.leanRpgPlan` still contains the used `{ chat, key, plan }`: the settle result short-circuits the RPG's clear at `src/v2/lean-rpg/precall.js:136`. A `none` plan with a reply containing no accepted lines also remains, because `src/v2/turn.js:795` skips the hook. This violates the next-generation-only/clear-when-used metadata contract.

12. **Valid cards can silently suppress the death card.** The checker allows four cards per block (`src/v2/data-modules/check.js:410`), but only eight total slots are registered in `src/v2/data-modules/part.js:253` and `:275`. Repro: define two ordinary chat blocks with four always-true cards each, then the stock Character and make `alive` false. `blockCards(head)` contains nine cards with `The story ends here` ninth, but the registered slots expose only the first eight. The death/end notice is never rendered even though its condition holds.

13. **Fight shows an empty foe as present while the planner refuses it.** `src/v2/lean-rpg/view/party-data.js:90` treats any named slot as filled and clamps count 0 to 1; `src/v2/lean-rpg/read.js:100` correctly requires count > 0. Repro: define the stock Foes block, then use its normal Blocks pencil to set `foe1` to `Rat` while `count1` remains 0. `hasFoes` is true and Fight shows one Rat, but `readSheet` reports that slot as `filled: false`, so the planner sees no Rat and cannot roll against it. The template itself specifies count 0 means empty. A second normal path has the same discrepancy: create two Foes blocks, leave the first empty and fill the second. Fight displays the second block’s Rat, while `readSheet` only reads the first Foes block (`src/v2/lean-rpg/read.js:137`) and tells the planner that there are no foes.

14. **Turning RPG off and on moves an inline battle log out of the story.** `src/v2/lean-rpg/view/battle-log.js:304` consumes the displayed marker, while `:473` destroys the panel without restoring the marker; `src/v2/ui-host.js:829` destroys and remounts on feature changes. Repro: render a real roll on a reply with a whole-line `[battle]`, toggle the feature off and on without re-rendering the SillyTavern message. The first panel is `inline`, but the remounted panel becomes the fallback `card` because the DOM marker has gone; the underlying chat still contains the marker. The log no longer appears at the approved location until the message is rendered again.

15. **Fight forgets the last exchange after 15 quiet turns.** `src/v2/lean-rpg/view/battle-log.js:389` only searches the last 30 chat messages, counting reader messages as well as replies; `src/v2/lean-rpg/view/fight.js:86` uses that result for Last exchange. Repro: keep a Rat in the Foes block, make one rolled attack, then send 15 ordinary messages whose planner answers `none`. The foe is still present, but `battleLog.latest()` changes from the attack reply index to null, and Fight loses its Last exchange panel and link although the roll is still in the chat.

16. **Replanning can reassign dice to an unaffected companion.** `src/v2/lean-rpg/resolve.js:106` removes refused actions before rolling, and `:158` consumes one sequential stream only for the surviving actions. Repro on the real host: start with Wessel, Ren, and Rat; an earlier reply makes Wessel Down. The next reply plans Wessel then Ren against Rat. Wessel is refused and Ren receives the first pair of dice. Delete the earlier Down reply: the later `rpg.resolve` replans with the same seed and Wessel now consumes the first pair, so unchanged Ren receives the second pair. In one run Ren changed from `(1, 19)` to `(9, 8)` despite the exact same seed, stat, opponent and planned action. Rebuild retains the new values; old prose can now disagree because the dice moved, not because Ren's modifiers changed.
