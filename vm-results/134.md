1. **Some labelled checkboxes and radios lose the 44px target.** Story_block `src/v2/view/size.css:54-67` gives dimensions only to a label with an immediate input child, but suppresses the input's `::after` whenever the input has *any* label ancestor. Repro on a phone in a supported authored screen: `<label><span><input type="radio" name="choice" value="x"></span> X</label>`. The renderer preserves this nesting; the label matches no sizing rule and the input gets no enlarged target. Even `<label><input type="radio" name="choice" value="x"> X</label>` can remain short: a plain label is inline, and `min-width` and `min-height` do not size a non-replaced inline box. **Fix:** size labels containing descendant checkbox/radio inputs, and give otherwise-inline labels a sizing-capable display such as a low-specificity `inline-block` fallback while retaining existing flex/grid labels. Continue to reserve the separate `::after` and margin for truly unlabelled inputs. Add rendered-size tests for direct and nested inputs as well as the existing loot chips.

2. **Some running-text links and inline role buttons still miss 44px.** Story_block `src/v2/view/size.css:29-31,88-89` applies minimums to all links and `role="button"` elements, but its `inline-block` rule covers only links with particular direct parents and explicitly excludes role buttons; its role-button rule covers only certain text tags. Repro on a phone in an authored template: `<div>Read <a href="#help">?</a></div>` or `<p><a href="#help" role="button">?</a></p>`. Both survive the renderer, remain ordinary inline anchors, and ignore the width/height minimums. **Fix:** provide a sizing-capable inline-box default for ordinary links regardless of text container, including links with `role="button"` or `role="tab"`, and for other inline role buttons; preserve explicitly styled flex/grid controls and keep the layout-participating padding without negative margins. Test these cases and adjacent controls.

3. **A supported color field is still narrower than 44px.** Story_block `src/v2/view/size.css:33-35` sets the field minimum height but no minimum width, the field-width part of Job 132's finding. Its own `src/v2/view/controls.css:95-102` makes a color input `2.4em` wide. Repro on a phone with default SillyTavern font scale and Suite zoom: render `<input type="color" aria-label="Color" data-draft="shade">` in a supported screen. At the default 15px input font and 0.8 zoom, its 2.4em width is 28.8 screen pixels before padding and borders; even including those it is below 44px. The template renderer preserves this input. **Fix:** add a zoom-adjusted 44px minimum width to the applicable phone/touch field rule, using border-box sizing as needed, and test a color input and a short select without expanding controls outside Suite roots.
