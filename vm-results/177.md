## Focus findings

1. Legacy rule cannot change a block that applied before. `validateScene` has refused a case-insensitive duplicate in `present` since the domain was written, and `step()` skips a replayed block that brings any new validator problem. So an unmarked `add /domains/scene/present/-` whose name the list already holds always ended as a skipped block on every earlier version; the new rule only turns that into "passed over, rest of the block applies". The only way an old block escaped the skip would be a state that already carried the identical duplicate Problem before the block (the "problem the state had before" forgiveness); live commands are validated, so I could not produce one. Theoretical only.
2. A second person differing only in case: not a valid state (validator refuses it), so nothing legitimate is lost. The first spelling stays, as in 2.11.1 (cosmetic).
3. An append that should apply because an earlier op of the same block removed the name: diffs never emit an index remove, a removal is always a whole-list `replace` (or a parent write), and `writtenAbove` sees both, so the append is kept as written. Checked by script (`mytests/rb.mjs`) and by the same-block scenario.
4. Narrow: with the same call on main and on 2.11.2, only `add /domains/scene/present/-` changes (passed over when held). Unchanged and kept: `scene/tags/-`, `scene/present2/-`, `scene/sub/present/-`, `x/present/-`, `mounts/list/-`, `scene/present/0`, a `replace` of the list, a live (not replayed) call, a parent `replace /domains/scene` earlier in the block, a state with no list. It uses `toLowerCase`, same as the validator.
5. Pinned/checkpointed old chats: when an OLD run wrote a checkpoint after a skipped block (needs a delete, then further sends), 2.11.2 trusts that checkpoint. The head keeps the OLD outcome and the old Problem stays listed ("Some changes stored on message N were not applied") until a replay starts from before that checkpoint (an earlier delete, edit or Re-read), when the block becomes kept. In my fuzz this showed as stale Problems with an unchanged head (15 of 200 steps at checkpoints every 1, 3 of 1350 at every 2); I reproduced a stale place with a hand chat (`mytests/cp2.mjs`: place stays Inn after load and after a further send, Problem listed). No data is lost and nothing wrong is written; it is the same lazy catch-up any replay change has. Follow-up 1.
6. Downgrade: a chat written by 2.11.2 (marked place-with and pencil ops) loads on main and on 2.10.0 with the same head and no Problem.
7. `dropEcho` models capture.js correctly and hides nothing. `splitEchoes` takes a story line that equals a block line out of the story, so it counts once. I confirmed in the product, live, on main and on 2.11.2 alike: `+ coin 7`, `+ item Torch | qty: 2`, `- item Torch`, `- coin 3 | to: the ferryman` each written in the block and again in the story apply once. Without `dropEcho` the four seeds fail on 2.11.2 with the model one too high (40 vs 39, 331 vs 337, 37 vs 36, 43 vs 42, product lower); with the new model the four seeds also pass against main's product code, so the product did not change and the failure was only in the model.
8. Oracle (`strictApply`) copies the legacy rule, so the delete-fuzz does not test that rule independently; it is covered by the new counters tests plus my differential runs, which use the product only.
9. Test edits: two assertions that pinned the old behavior were changed (oracle-validators now writes the duplicate as a whole list; counters "unmarked op" now uses another domain); a legacy-rule test and two end-to-end tests (place with, pencil set; each with rebuild == live and reload == live) were added. Nothing weakened or skipped.
