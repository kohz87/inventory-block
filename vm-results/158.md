## Blockers

### B1. A `prompt: false` RPG field still reaches the narrator through the roll planner and cue

The 155 B2 tail repro is fixed, but the hidden-field promise is still broken end to end. `readSheet` reads raw fields without consulting their schemas (`src/v2/lean-rpg/read.js:67` and `:127`); `sheetText` sends them to the planner (`precall.js:49`), and a plan naming such a field is turned into a `[Rolls]` cue for the narrator.

Real-host repro: enable RPG, define the stock Character with `who.default = 'Wessel'`, and define a chat-scoped `role: 'foes'` block with `kinds: {}` and fields `foe1: {type:'text', max:40, default:'SECRET BARON', prompt:false}`, `count1: {type:'int', min:0, max:3, default:1}`, `class1: {type:'int', min:1, max:9, default:1}`, and `hurt1: {type:'int', min:0, max:5, default:5}`. Both definitions are accepted. Have the planner answer `act Wessel | stat: STR | target: SECRET BARON`, then send a reply. The planner prompt contains `SECRET BARON`, the saved `rpg.resolve` summary contains `Wessel → SECRET BARON`, and the actual narrator request contains it too. The direct role tail omits the name. Thus a pack can hide a name from the tail yet reveal it to the story through a normal automatic roll. Existing `fix4a.test.js` B2 checks the tail and request without exercising a planner that selects the hidden name.

### B2. Eight reply-end subjects leave no evaluation budget for any story block action

`settleSteps` counts each subject, and `finish` reserves `kept * 2048` visits out of the reply's 16,384 (`src/v2/data-modules/part.js:252,330-341`). At eight subjects the allowed number of visits for story actions is zero, even on a fresh reply. This is independent of the 32-root cap and occurs even though the actual stock settles are small.

Real-host repro: after an opening reply, define eight copies of the stock Character template with distinct slugs `hero-0` through `hero-7`, distinct names, and distinct `who` defaults. All eight `dm.define` calls succeed. On the next reply send `~ dm hero-0 — hit | kind: set-health | to: Hurt` inside `<Changes>`. The very first block action is refused with `DM_BUDGET` / “This reply has used all the block actions it can take, and the last place is kept for settling it”; health remains 5 and no receipt is recorded. With seven otherwise identical Character blocks, the same line succeeds, health becomes 3, and seven settles are recorded. A pack with attached character-scoped subjects can hit the same multiplication. The original B8 test covers one settlement, not this supported multi-subject boundary.

### B3. Eight other end-tone cards can still suppress the death card

The lead decision says an end-tone card always gets a slot. Sorting end before warn and info is insufficient when more than eight end cards are true (`src/v2/data-modules/part.js:261-285`): ties retain pin order and the socket still exposes only eight cards.

Real-host repro: define two ordinary valid chat blocks `one` and `two`, each with one boolean field, `kinds: {}`, and four cards `{type:'card', when:true, tone:'end', title:'one 1' /* distinct title */, text:'End.'}`. Then define the stock Character. Send a reply setting its health to Down, followed by a reply with the accepted `~ place Dungeon | kind: ruin` line. Its `alive` is now false. `blockCards(head)` returns nine cards with `The story ends here` at index 8; `block-card-1` through `block-card-8` show the other eight and omit the death notice. The 155 B12 test only competes against info and warn cards.

### B4. Re-reading an old, unversioned roll can add an exchange that was not recorded originally

The `dice` version correctly retains the old sequential RNG stream, but `rollPrepared` uses the new `fitCue` for old payloads too (`src/v2/lean-rpg/resolve.js:208-215,250-254`). The old algorithm retained one oversized round; the new shortening can fit two. A Re-read recalculates the number of stored rounds and silently changes the old battle log, although the seed and first round are unchanged.

I generated an actual chat on `9228472` and loaded it on `4ce3111`. Define six legal chat Character role blocks and one Foes role block, as in the shared long-name repro below; give all characters STR 10, AGI 10, health 5 and all four foes count 1/class 1. Set custom `decisiveMargin` to 15. Use the plan below, and fix `crypto.getRandomValues` for `Uint32Array` seed draws to 12, forwarding other draws to the real crypto implementation. On `9228472`, the saved `rpg.resolve` has seed 12, no `dice` field, one round, and `stop: 'budget'` (the cue is 729 estimated tokens). Load the saved chat at `4ce3111`: it still shows one round and has no replay problems. Re-read the unchanged reply: it succeeds, retains seed 12 and the identical first round, but now has **two** rounds and `stop: 'decisive'`, with no replay problem. A previously absent exchange is now presented as part of that old reply. The existing old-payload B16 test checks sequential draw order, not an actual cross-version Re-read or the round count.

### B5. Cue shortening can erase the identity of every participant

At `src/v2/lean-rpg/cue.js:14-29,66-75`, shape 3 truncates every name to the same first 19 characters plus an ellipsis, without checking for collisions. The roll record still identifies the participants, but the narrator cannot associate outcomes with them. This is a regression in the B4 fix, even though the cue now fits its 600-token cap.

Real-host repro: use six distinct legal names and four distinct foe names made as follows; text fields with `max: 60` are accepted. Each Character needs `who`, STR, AGI and health fields; one chat Foes block holds the four names with count 1. The planner can answer using the short, uniquely matched suffixes and numeric foe slots; the complete answer is only 589 characters:

```js
const names = Array.from({length: 6}, (_, n) =>
  'Captain Rare Long Common Name '.padEnd(54, 'x') + `pc${n}`);
const foes = Array.from({length: 4}, (_, n) =>
  'Mysterious Dangerous Long Foe '.padEnd(54, 'y') + `foe${n}`);
const answer = [
  'pace: all',
  ...names.map((_, n) => `act pc${n} | stat: str | target: ${n % 4 + 1}`),
  ...foes.map((_, n) => `foe ${n + 1} | target: pc${n} | defend: agi`),
  ...names.slice(0, 4).map((_, n) =>
    `check pc${n} | skill: Phantom | stat: str | difficulty: very hard`),
].join('\n');
```

The real receipt held six distinct acting characters and four distinct foes, but its narrator cue called every character `Captain Rare Long C…` and every foe `Mysterious Dangerou…`; its checks and attacks included different successes and failures. The pinned cue reaches the narrator but does not say which individual earned each result. The existing max-plan test verifies length and check count, not distinct identities.

### B6. Character-scoped role blocks appear in Fight but are ignored by the planner

The role checker allows character scope and the views deliberately iterate its attached subjects (`src/v2/lean-rpg/view/party-data.js:57-68`). The planner's `fieldsOf` looks only under `.chat`, skipping every such instance (`src/v2/lean-rpg/read.js:67-70,121-141`). The shared brief says a block with a role is read by RPG; the B13 fix's promise that all Foes blocks are read therefore remains incomplete.

Real-host repro: create a host with the testkit `directorStub()`, enable RPG, and define a stock chat Character named Wessel. Install a valid pack containing the stock Foes definition with `scope:'character'`, `foe1.default = 'Rat'`, `count1.default = 1`, and attach it to `ca_wessel01` using `dm.pin`. Installation and pin succeed. `readFight(head)` contains Rat, but `readSheet(head).foes` is `[]`. With the planner answer `act Wessel | stat: STR | target: Rat`, no `rpg.resolve` is recorded; the planner reports the answer could not be read. The existing B13 tests cover chat-scoped blocks only. Character-scoped Character and Skills role instances are likewise skipped by `readSheet`.

### B7. Turning RPG off during generation leaves the used plan in chat metadata

The new `afterReceive` calls `precall.afterCapture`, but that clear is conditional on the feature still being on (`src/v2/lean-rpg/index.js:57-59`, `precall.js:144-146`). The original B11 cases pass while the feature remains on; the next-generation-only metadata contract still fails if a reader switches it off while the reply is in flight.

Real-host repro: turn RPG on, define Wessel and a filled Rat foe, and let the planner answer `act Wessel | stat: STR | target: Rat`. Wrap the test host's interceptor so that after the original interceptor resolves, but before the reply arrives, it calls `host.features.set('story-block.rpg', false)`. At that point `ctx.chatMetadata.rpgPlan` holds the plan. Complete the reply. It records `rpg.resolve`, but `ctx.chatMetadata.rpgPlan` still holds `{chat, key, plan}` after `afterReceive`. The clear should not depend on the current toggle after a plan has already been used.

### B8. Reset can leave the unsaved Combat edit active while displaying the default

The new `focusout` save and Reset race in `src/v2/lean-rpg/view/settings.js:238-256`. `block.prompt` is updated only after the asynchronous save completes. If Reset is clicked during that wait, its desired default equals the stale `block.prompt`, so the second `save()` returns without writing it. The first save then wins.

Real UI/testkit repro: open Settings → RPG with the default Combat rules block, type `Unsaved edit`, and leave the textarea by clicking Reset while the first `dm.redefine` is still pending. I used `page()` from `tests/v2/lean-rpg/view/page.js` with a command wrapper that calls the real `host.sdk.command` and delays its `dm.redefine` result by 150 ms; dispatch `focusout`, wait 10 ms, then click `[data-act="combat-reset"]`. After completion, `combatBlock(host.head()).prompt` is `Unsaved edit` and there is only one redefine receipt, although the textarea displays the default. The SDK can wait on a save before returning (`src/v2/sdk.js:462`), so this is not limited to a fake command. Existing Reset coverage waits for the first save to finish before clicking.
